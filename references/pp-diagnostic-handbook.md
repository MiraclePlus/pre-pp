# PP 诊断手册 — 路演 Pitch 常见问题分类与案例库

> 来源：MPR | 校友PP参考手册(F25)
> 飞书文档：https://miracleplus.feishu.cn/wiki/IQLuwdguhisFCukAAXCcq31SnDP

本文档是 pre-PP 审阅模式的核心诊断依据。按 6 大故事线维度组织，每个维度下列举常见问题类型及真实案例。

---

## 1. What — 一句话描述公司/项目做什么

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 1.1 | 表达不清晰、结构混乱 | 开头内容混乱，视觉误导，观众无法在30秒内理解项目 |
| 1.2 | 项目定位模糊或前后不一致 | 定位在 ToB/ToC 间摇摆，用词宏大但缺乏解释 |
| 1.3 | 产品展示不具吸引力或存在误导 | 产品截图粗糙，首图不清晰，无法快速传达做什么 |

### 诊断标准

- **30秒测试**：观众能否在前30秒内准确复述"这家公司做什么"
- **一句话定位**：是否有清晰的类比（如"XX领域的YY"）
- **视觉一致性**：首页视觉是否与实际业务匹配，有无误导
- **术语检查**：是否使用了需要解释的术语而未解释

### 典型反面案例

- 遥动科技：首页"扫帚+门"视觉误导，观众以为项目讲"拖把"
- 万物有灵：宏大术语（"本体""具身智能"）与实际（教育机器人）落差大
- AILSI：公司名与创始人名混淆，观众不清楚公司叫什么
- 得斯笔记："从对话工具向思维伙伴的跃迁"等学术化表述未关联具体场景
- SoMark文档智能：未明确类比（如"大模型时代的Scale AI"），导致投资人反复追问差异化

### 修正建议

1. 用"一句话公式"：`[公司名] 是 [目标用户] 的 [核心价值]`
2. 如果复杂，用类比：`[知名公司] for [新场景]`
3. 首页视觉必须与业务直接关联，禁止无关配图
4. 术语必须在首次出现时用大白话解释

## 2. Why Now — 痛点/需求/机会

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 2.1 | 逻辑割裂/表述混乱，痛点不成体系 | 前后页逻辑断裂，主题突然跳转 |
| 2.2 | 概念堆叠/表达过载 | 术语密集，缺乏层次感，观众无法消化 |
| 2.3 | 问题陈述过长/缺少解决方案 | 花大量时间讲问题，不讲怎么解决 |
| 2.4 | 亮点表达平淡/痛点不够突出 | 有优势但语气平淡，未制造冲击感 |
| 2.5 | 痛点表述夸张/缺乏信服力 | 过度夸大，理由不充分 |
| 2.6 | 痛点阐述冗余/众所周知 | 讲常识性内容（如"半导体很重要"） |
| 2.7 | 痛点缺乏场景化/视觉化支撑 | 无具象故事、无量化数据 |

### 诊断标准

- **新信息测试**：观众是否获得了新信息（vs 已知常识）
- **场景化**：痛点是否有具体场景/故事/数据支撑
- **逻辑链**：痛点→机会→解决方案是否形成完整链条
- **信服力**：数据来源是否可信，表述是否克制
- **时间分配**：痛点陈述是否占比过大（建议≤2页）

### 典型反面案例

- 遥动科技：前几页逻辑割裂，未形成连贯叙述
- 全景效应：吊胃口不给解法（讲"上下文"→突然跳到agent重塑组织）
- 得斯笔记：概念堆叠（notion、AI、协同、知识孤岛），字多语速快
- 万物有灵：花大量时间讲"当今问题"而非解决方案
- SOMA Robotics：表述争议多，过于夸大
- 澜紫微电子：讲"半导体重要性"等常识
- 偶域："SKU无法覆盖角色数量"未通过具象故事传递
- 探微杜渐：未用真实案例说明业务漏洞后果

### 修正建议

1. 痛点必须场景化：用"某某企业/用户遇到了XX，导致YY损失"格式
2. 量化：有数据就用数据，无数据用具象类比
3. 控制篇幅：痛点≤2页，解决方案才是重点
4. 避免已知常识：如果观众都知道，一句话带过即可
5. 痛点与场景一一对应：每个痛点匹配一个具体场景

## 3. How — 产品/解决方案

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 3.1 | 产品描述模糊/没讲清楚在做什么 | 概念多但无具体产品说明 |
| 3.2 | 技术与实际应用脱节/视觉不连贯 | 技术突然出现，与场景无关联 |
| 3.3 | 产品细节不明确/表达缺乏深度 | 术语混乱，信息堆叠 |
| 3.4 | 配图/表达产生误导 | 图片让人误解产品定位 |
| 3.5 | 产品定位反复横跳 | ToB/ToC不统一，主线不清 |
| 3.6 | 技术叙述堆砌/无产品实质 | 堆技术词但不讲做什么产品 |
| 3.7 | 没有展示产品设计或特性 | 缺产品截图/demo/设计图 |
| 3.8 | 偏离核心/解决方案不聚焦 | 解决方案与痛点不匹配 |
| 3.9 | 表达冗长/未突出重点 | 内容需简化 |

### 诊断标准

- **可视化测试**：是否有产品截图/demo/流程图
- **一致性**：产品是否与前面讲的痛点直接对应
- **深度vs广度**：是否聚焦核心功能而非面面俱到
- **技术翻译**：技术细节是否翻译为用户价值
- **误导检查**：配图是否会产生错误联想

### 典型反面案例

- 得斯笔记：没把"我们到底在做什么"讲清楚
- SOMA Robotics：概念多、用词不当（如"唤醒"），不知具体产品
- AILSI：内容从"多肽"跳到"AWS"，割裂
- 遥动科技：人脸识别出现引发误解，以为是"刷脸"项目
- 万物有灵：配图让人误以为是儿童玩具
- 全景效应：产品细节模糊，让观众怀疑是"一个壳子"
- 澜紫微电子：技术优势堆叠但不讲产品是什么

### 修正建议

1. 必须有产品截图或demo视频（哪怕是原型）
2. 用"用户故事"格式：用户做XX → 系统做YY → 结果是ZZ
3. 技术→价值翻译：每个技术点对应一个用户可感知的好处
4. 聚焦核心功能（最多3个），不要面面俱到
5. 配图必须是自己的产品，不用通用素材

## 4. Why（市场） — 市场有多大

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 4.1 | 市场逻辑表达不清/缺乏完整推演 | 提到大市场但未说明如何切入 |
| 4.2 | 缺乏具体客户/市场入口虚浮 | 列大公司名但无实际客户 |
| 4.3 | 市场定位或表达不清晰/场景不匹配 | 市场切入与技术应用不匹配 |
| 4.4 | 商业模式空洞/无实质支持 | 声称"模式清晰"但无具体内容 |

### 诊断标准

- **TAM-SAM-SOM**：是否有从大到小的市场切割逻辑
- **入口客户**：是否点名了第一批付费客户是谁
- **商业模式**：收费方式、单价、频次是否清晰
- **增长逻辑**：从第一个客户到规模化的路径

### 典型反面案例

- 得斯笔记：提到"挑战谷歌、微软"引发质疑
- 模思：提到ASML、台积电，但未说明实际客户是谁
- SOMA Robotics：声称"商业模式清晰"但无任何具体内容

### 修正建议

1. 市场数据必须有来源标注
2. 从具体客户出发，自下而上推算市场
3. 商业模式用公式：`[客户类型] × [单价] × [频次] = 年收入`
4. 不要用行业大报告的TAM，用自己能触达的SOM

## 5. Why Us — 创始人团队

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 5.1 | 团队背景未突出/亮点埋没 | 有强背景但表达太弱 |
| 5.2 | 信息杂乱/没有重点 | 密度高但无主次 |
| 5.3 | 团队照片或展示方式不当 | 无关照片、不专业 |
| 5.4 | 团队特色未对齐业务重点 | 强调学术但业务需要销售能力 |
| 5.5 | 团队背景强但未放大亮点 | 如有Tesla背景但未突出 |

### 诊断标准

- **匹配度**：团队亮点是否与业务需要对齐
- **记忆标签**：是否有让投资人记住的"标签"（如"前Tesla"）
- **分工清晰**：技术/商务/产品角色是否明确
- **补充关系**：团队成员是否互补而非重叠

### 典型反面案例

- 得斯笔记：实际是"非常强的团队"但pitch中完全没展现
- 模思：上海AI圈、教授带队本应是亮点，表达太弱
- 遥动科技：信息密度高但未突出重点
- 空天探索：技术不特别硬核但强调学术背景，应强调销售能力
- SOMA Robotics：有Tesla背景但未放大

### 修正建议

1. 每个人只讲一个"最强标签"：`[名字]，前[知名公司/学校]，[核心能力]`
2. 团队亮点必须对齐业务：技术型公司突出技术leader，商业型突出BD能力
3. 用数字量化经验：`10年XX经验` / `管理过XX人团队` / `0到1做过XX产品`
4. 如果有知名公司背景，放大：logo + 具体成就

## 6. Traction — 进展

### 问题类型

| # | 问题 | 表现 |
|---|------|------|
| 6.1 | 进展数据空泛/缺乏量化 | 泛泛而谈无具体数字 |
| 6.2 | 项目状态/节奏不清晰 | 不知道现在到哪一步了 |
| 6.3 | 没有将进展转化为投资亮点 | 有数据但未突出意义 |
| 6.4 | 有亮点但未高亮/未视觉化 | 强数据但视觉不突出 |

### 诊断标准

- **量化**：是否有具体数字（收入/用户/增长率/合同数）
- **时间线**：是否展示了清晰的里程碑节奏
- **增长曲线**：数据是否呈上升趋势
- **视觉突出**：关键数字是否被放大/高亮

### 典型反面案例

- Infotopia：不够具体，观众期待更多时戛然而止
- 澜紫微电子：突然跳入英文内容，收尾无力
- 全景效应：缺乏差异化，没说明为什么能赢
- AILSI：有需求有单进展快，但未具体阐述
- 素源矩阵："5元/吨"节省不具冲击力，应改为"总共省了XX万"
- 遥动科技：有"3个月迭代4次"的强势点但未突出

### 修正建议

1. 关键数字必须单独占一行/一块，字号≥36pt
2. 用对比增强冲击：`传统XX天 → 我们XX小时`
3. 进展用时间线展示：`月份 → 里程碑 → 数据`
4. 有增长就画曲线图，视觉比文字有说服力10倍
5. 用绝对值对比，不用比例（"998元 vs 7000元"而非"1/7"）

## 通用视觉/表达规范

### 视觉原则

| 规则 | 说明 |
|------|------|
| 一页一重点 | 每页只传达一个核心信息 |
| 图大字少 | 配图占60%以上面积，文字精简 |
| 对比突出 | 数据对比用视觉（大小/颜色）而非文字 |
| 无误导配图 | 图片必须与内容直接关联 |
| 字号下限 | 正文≥24pt，关键数字≤54pt，最大最小字号差≤30pt |

### 表达原则

| 规则 | 说明 |
|------|------|
| 先结论后解释 | 金字塔原则：结论→证据→细节 |
| 用大白话 | 避免术语；必须用时先解释 |
| 控制信息密度 | 每页≤5个信息点 |
| 有节奏 | 紧张（痛点）→舒缓（方案）→高潮（数据） |
| 类比优先 | 复杂概念用"XX领域的YY"一句话带过 |

## 使用方式

pre-PP 审阅模式（Phase 0B）中：
1. 按 6 大维度逐一诊断
2. 对每页 slide，检查是否命中本手册中的问题类型
3. 输出格式：`[页码] [维度.问题编号] [问题描述] → [修正建议]`
4. 严重度标记：🔴 致命（必须修改）/ 🟡 建议（可选修改）/ 🟢 优化（锦上添花）
